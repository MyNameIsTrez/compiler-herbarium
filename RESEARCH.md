# Research dump

A running list of links to compiler designs, papers, posts and repos that are relevant to this repo. It has three tables:

1. Leads that already have an entry in this repo.
2. Leads that do not have an entry yet, and still need to be investigated.
3. Leads that were considered and declined.

When a lead gets an entry, move its row from the second table to the first. New leads usually arrive as issues, see [CONTRIBUTING.md](CONTRIBUTING.md).

The "Read" column says whether the lead has been read in enough depth to rely on, not just listed. ✅ means read, ❌ means not read yet. A ✅ says what was read and what was not, because it often means one part of a larger source. Many ✅ rows were read by research subagents on 2026-11-10, and their claims were not re-checked by hand. The "What it could become" column holds a verdict on whether the design adds anything over the existing entries, and rows that add nothing move to the declined table.

## Considered and declined

These do not pass "What earns an entry" in the [README](README.md).

| Lead | Why declined |
|------|--------------|
| A language that only lowers to LLVM IR | The back end would repeat `distilled/clang`. The front end, a language-specific lowering, is the part this repo leaves out. A design whose middle IR is the interesting part, such as MIR in rustc, is judged on that IR instead. |
| Bantam | A Pratt parser demo. The repo leaves out the parser. |
| Brainfuck compilers | Eight commands map nearly one-to-one onto machine code. There is no IR, scoping or type system, so the compiler is a table. `original/naive` already shows expanding code with no IR in between. |
| CakeML | The value of the verified back end is the HOL4 proofs, which a C file cannot carry. The pass chain (source, flat, closures, BVL, BVI, data, word, stack, lab, target) and the allocator choices (simple, IRC, linear scan) are conventional ML compilation that overlaps `distilled/qbe` and `distilled/clang`. Read in part: the JFP 2019 abstract, `compiler/backend` file list and the pass chain in `backendScript.sml`. |
| Finch | A prototype-based object model on a register bytecode with upvalues, in C++. Only the README and the opcode list in `Block.h` were checked. The register bytecode and upvalues repeat `distilled/puc-lua` and Bulfinch, and prototypes are an object model, not a compiler design. Worth a second look if prototype dispatch becomes a lead. |
| Ghuloum, An Incremental Approach to Compiler Construction | A methodology paper: tagged Scheme values compiled to IA-32 in 24 steps, with closure conversion. It has no IR of its own, and tagged values, closures and direct assembly are shown by `distilled/chibicc`, `original/naive` and `distilled/luajit-interpreter`. It is useful as a guide to how to build entries. The nanopass idea of one language per pass is part of the Lisp compilers row. |
| Idris 2 | The back end is conventional (lambda lifting, ANF, VM code) and its generators are thin layers over Chez, Racket and Gambit or a small C runtime. The distinctive part, quantity erasure from quantitative type theory, lives in the type checker, which this repo leaves out. Read in part: the QTT paper, `ANF.idr`, and function names in `Inline.idr`. |
| Jasic | A BASIC interpreter in one Java file. BASIC's statements and `goto` have trivial semantics. Only the file listing and README were checked. |
| Lark | A homoiconic Smalltalk-style experiment in Java. Only the README and directory listing were read. It differs in surface syntax and has no distinct IR or execution model. |
| LLVM bitcode | A serialization container (bitstream with fixed, VBR, char6, array and blob encodings, abbreviations and a BLOCKINFO block), with no compiler semantics. It would show abbreviation-driven encoding, but that is neither an IR design nor an execution model. The format page was read in full. |
| `mark-sweep` and `lisp2-gc` | Garbage collectors (mark-sweep, and LISP2 mark-compact), not compilers. A collector is runtime design, which this repo leaves out. A compiler entry that needs one can include the part it uses, as clox's `memory.c` would. |
| Turboshaft | A conventional SSA CFG with a dominator tree and a flat operation buffer addressed by `OpIndex`, which adds nothing over `distilled/qbe`, `clang` or `sea-of-nodes` beyond a contrast with Sea of Nodes (the V8 post is already used in the sea-of-nodes README). Its distinctive part, stacks of reducers, is C++ template mixins and does not carry to C17. Read in part: `graph.h`, the header of `ops.h`, the phase list in `pipelines.h` and `pipeline.cc`. |
| Umbra and Flying Start | Umbra's source is not open (a binary download, a proprietary license), and no open reimplementation of Flying Start was found, so there is nothing to distill from. The paper was read: an SSA IR in a compact array, mapped instruction by instruction to x86, plus stack-slot reuse and a live-span pass. |
| Vigil | A 105-line Python script that rewrites `implore` and `swear` lines with regular expressions into calls of helper functions and then `exec`s the result in Python. It is a thin layer over an existing back end. |
| WebAssembly as a standalone entry | A plain Wasm engine repeats the stack-VM execution of `distilled/puc-lua`, `cpython` and `original/naive`. The new part, validation by a typed abstract stack, is what Wizard and Winch build on, so the format is only an input for those leads. The spec pages were not read. |

## Cells of the design space map that will stay empty

The map at the top of the [README](README.md) has a crossed cell where this repo has decided not to add an entry, ever. A cell that is merely empty is a gap, not a decision, so only cells with a reason that holds for every design in them are crossed.

| Cell | Why it stays empty |
|------|--------------------|
| Analysis only, nothing in between | There is no representation to analyze, so the cell has no designs in it. |
| Analysis only, tree (AST) | Type checkers, linters and similar checks of source are front-end work, which this repo leaves out (it is also why Idris 2 is declined). |
