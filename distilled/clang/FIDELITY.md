# Fidelity: clang

Real design being mimicked: Clang and the LLVM code generator for x86-64, from `llvm-project` at commit `eb461b1bb3f5325f5f2054c4d9b94a5df03b704b` (a shallow, sparse clone of `main`).

Reference material used:

- Source: [llvm/llvm-project](https://github.com/llvm/llvm-project) at that commit.
- Read in depth: `llvm/lib/Transforms/Utils/PromoteMemoryToRegister.cpp` (`PromoteMem2Reg::run`, `rewriteSingleStoreAlloca`, the live-in computation, the forward IDF calculator, the rename pass), `llvm/lib/CodeGen/RegAllocBase.cpp` (`allocatePhysRegs`), `RegAllocBasic.cpp` and `RegAllocBasic.h` (the priority queue, `selectOrSplit`), `PHIElimination.cpp` (`LowerPHINode`: the `IncomingReg` scheme), `TargetRegisterInfo.cpp` (`getRegAllocationHints`), `LiveRegMatrix.cpp` (`checkRegMaskInterference`), `X86RegisterInfo.td` (the order of `GR64`), `clang/lib/CodeGen/CGStmt.cpp` (block names), `CodeGenFunction.cpp` (`retval` and the `return` block), `llvm/include/llvm/IR/ConstantFolder.h` (`FoldBinOp`).
- Skimmed only: `SelectionDAGISel.cpp` (the steps of `CodeGenAndEmitDAG`: combine, type legalization, legalization, combine, selection, scheduling), `TwoAddressInstructionPass.cpp` (the header comment and the names of the transforms).
- Not read: `LiveIntervals.cpp` and `LiveRangeCalc.cpp` (the interval construction here is written from the description of slot indexes and segments, not from them), `RegisterCoalescer.cpp`, `VirtRegMap.cpp` beyond finding that identity copies are removed, `PrologEpilogInserter.cpp`, `X86FrameLowering.cpp`, the x86 instruction patterns (`X86InstrArithmetic.td` and friends), the dominator tree construction (`GenericDomTreeConstruction.h`), `SelectionDAGBuilder.cpp`, `VirtRegAuxInfo.cpp` (spill weights) and the MC layer (encoding). Their stages are modeled on the names and the order of the passes, and on what the dumps of `llc` show.

## Stage mapping

| Stage in this entry | Real stage name | Where it lives in the real source | Kept | Dropped or simplified |
|---------------------|-----------------|-----------------------------------|------|-----------------------|
| `stage_irgen` | Clang CodeGen | `clang/lib/CodeGen/CGStmt.cpp`, `CodeGenFunction.cpp`, `IRBuilder` | IR where every local and parameter is an `alloca` in the entry block, read by `load` and written by `store`. The blocks of `if` and `while` are named as `CGStmt.cpp` names them, a function with several returns stores to `retval` and jumps to a block called `return`, and a binary operation on two constants is folded by the builder | The lexer, parser, AST, types and semantic analysis: the examples are hardcoded as the calls the AST walk would make. No attributes (`noundef`, `nsw`, `align`), no `llvm.loop` metadata, no lifetime markers. Real clang discards value names unless asked, so its own dump uses numbers |
| `stage_mem2reg` | `mem2reg` (`PromoteMemToReg`) | `llvm/lib/Transforms/Utils/PromoteMemoryToRegister.cpp` | An alloca with one store is rewritten in place (`rewriteSingleStoreAlloca`). Any other alloca gets PHIs on the iterated dominance frontier of the blocks that store, only where it is live-in. A walk down the dominator tree renames loads and stores. Phis are named after the alloca with a version number | The case of an alloca used in one block only (`promoteSingleBlockAlloca`), because no example has one. A single store that does not dominate a load falls back to the PHI path, as in the real pass, but a load that precedes every store reads zero instead of `undef`. No debug info, no lifetime intrinsics, no `llvm.assume`. The dominator tree uses the iterative algorithm, where LLVM uses SemiNCA. No other IR pass runs (no constant folding of instructions, no CFG simplification, no inlining), so a compare of two constants stays a compare |
| `stage_isel` | SelectionDAG instruction selection | `llvm/lib/CodeGen/SelectionDAG/SelectionDAGISel.cpp`, `SelectionDAGBuilder.cpp`, the x86 patterns | One DAG per block. A value that crosses a block, or goes into a PHI, lives in a virtual register; a constant going into a PHI gets a new register. Equal pure nodes are shared. Copies to registers, calls and branches are linked by a chain. Selection picks `ADD64rr`/`ADD64ri8`, `SUB64ri8`, `IMUL64rr`, `CMP64ri8` with `JCC_1`, `MOV64ri32`, `LEA64r`, `CALL64pcrel32`, `RET64`. The scheduler emits the chain first, then the operands. PHIs stay in the machine IR with a virtual register per incoming edge. The argument comes in `rdi`, the result goes out in `rax` | The combine and legalization steps (`DAGCombiner`, `LegalizeTypes`, `LegalizeDAG`) are left out, so nothing is folded or reassociated. Selection is a `switch` over the shapes in the examples, not the tablegen matcher: the right side of a `sub` and of a compare must be a constant. No addressing modes, no `LEA` for a three-address add, no commuting, no `DEC`/`INC`. The scheduler is a depth-first walk, not the list scheduler. The branch to the next block is not dropped here, but when encoding. A value computed in a block is selected straight into the register that another block reads, which is what the register coalescer would make of a copy |
| `stage_phi_elim` | PHIElimination | `llvm/lib/CodeGen/PHIElimination.cpp` | `d = PHI s1, bb1, s2, bb2` becomes `d = COPY t` at the top of the block and `t = COPY s_i` before the terminators of each predecessor, with a fresh `t` per PHI | The reuse of `t` between PHIs that share an operand, the special cases for operands defined by another PHI, for critical edges and for `IMPLICIT_DEF`, and the updates of live variables |
| `stage_two_address` | TwoAddressInstruction | `llvm/lib/CodeGen/TwoAddressInstructionPass.cpp` | `A = op B, C` becomes `A = COPY B` and `A = op A, C` for the x86 arithmetic that overwrites its first source, which leaves `A` with two definitions | Commuting the operands when the other one dies, conversion to three-address form (`LEA`), and the scheduling of the copy next to its definition. Always inserts the copy |
| `stage_live_intervals` | LiveIntervals | `llvm/lib/CodeGen/LiveIntervals.cpp`, `LiveRangeCalc.cpp`, `SlotIndexes` | Each instruction gets slots for its uses and its defs. An interval is a list of segments in slot order, merged when they touch. A physical register used by the next instruction gets a fixed range, and a call is a register mask at its slot | Not read. One segment per block per register (so a register that is dead in the middle of a block counts as live), no value numbers, no sub-registers, no register units, no dead-def slots, no early-clobber slots. The spill weight is `references * 1000 / size`, where LLVM weighs each use by block frequency and loop depth (`VirtRegAuxInfo`) |
| `stage_coalesce` | RegisterCoalescer | `llvm/lib/CodeGen/RegisterCoalescer.cpp` | A copy between two virtual registers is removed by joining them when their intervals do not overlap | Not read. It joins only on a plain overlap test: no value-based joining of overlapping intervals, no joining with physical registers (hints do that), no rematerialization, no sub-registers, no ordering of the copies by loop depth. Intervals are rebuilt after each join |
| `stage_regalloc` | RABasic | `llvm/lib/CodeGen/RegAllocBasic.cpp`, `RegAllocBase.cpp`, `AllocationOrder.cpp`, `LiveRegMatrix.cpp` | A priority queue of intervals by weight, ties to the higher register number. The next interval tries its hints (the registers its copies point at, or that the other end of a copy already has), then the registers of `GR64` in their order. A register is refused if its fixed range overlaps, if an interval already in it overlaps, or, for a caller-saved register, if a call is inside the interval, so a value that is live across the recursive call in `fact` ends up in `rbx`. The rewriter then replaces the registers and drops the copies that became no-ops | Spilling, live range splitting and eviction (RABasic spills the lowest weight, RAGreedy splits). The program stops if no register is free. Only the registers up to `rbx` are in the order, since no example needs more. The real queue is a `priority_queue` over `CompSpillWeight`; this is a scan for the largest key |
| `stage_prologue_epilogue` | Prologue/epilogue insertion | `llvm/lib/CodeGen/PrologEpilogInserter.cpp`, `llvm/lib/Target/X86/X86FrameLowering.cpp` | A function that uses a callee-saved register pushes it at the top and pops it before each return | Not read. No stack slots, no frame pointer, no stack alignment, no `ADJCALLSTACKDOWN`, no red zone, no CFI |
| `stage_encode` | MC code emission | `llvm/lib/Target/X86/MCTargetDesc/` (the MC code emitter) | Machine instructions become bytes, with `rel32` fields patched once every offset is known | Not read. No short jumps, no relaxation, no ELF object. `print_int` and `print_str` are bytes of this entry, where the real program calls into libc |
| `stage_export` | Linking and loading | the linker and the OS loader | The code is placed in executable memory and run | The code goes into an anonymous `mmap`, is made executable with `mprotect` and is called. No object file is written. `code.bin` holds the raw bytes |

## Deliberate deviations

- No middle end beyond mem2reg: the optimizing pipelines run many more IR passes, which are not distinctive to this design and would fold the examples away. The dumps therefore show what the back end does with unoptimized-looking IR.
- A pipeline of passes runs over the whole function, as in LLVM, but there are no analysis managers: each stage recomputes what it needs.
- The examples are not parsed. A function per example calls the same builder operations that clang's code generation would.
- The dump numbers virtual registers from zero and prints `%N`, without the register class (`gr64`) and the flags (`killed`, `dead`) that LLVM prints.

## Comparison with the real tool

Command: `clang -S -emit-llvm -O0 -Xclang -disable-O0-optnone fact.c`, then `opt -passes=mem2reg -S`, with clang 23.1.3 and C versions of `fact` and of the loop.

- Matches: the IR of `fact` and of the loop has the same alloca, load, store and block structure as the `stage_irgen` dump, including the two stores to `retval` and a `return` block with one load. After `mem2reg`, `fact` has the same PHI `[ 1, %if.then ], [ %mul, %if.end ]`, and the loop has a PHI for each of `sum` and `i` in the loop header, with the same incoming values.
- Differs: real clang prints numbered values (it drops the names) and adds `noundef`, `nsw` and `align 8`. The two PHIs of the loop are in the opposite order (real: `i`, then `sum`). For `llc` the stages after this one (SelectionDAG, PHI elimination, register allocation) were only compared by eye with `llc -print-after=phi-node-elimination` on `fact`: it shows the same virtual register copied from `$rdi`, the same `JCC_1`/`JMP_1` pair, and a call with a regmask. It runs on IR that was not promoted, so it has stack slots (`MOV64mr`) where this entry has registers, and it folds the compare and the decrement into `CMP64ri32` and `DEC64r`.

## Regenerating expected.txt

Every `examples/<name>/expected.txt` is the output of real Lua 5.4 on that example's `program.lua`, so it does not rest on this entry. Never edit one by hand. From the repository root:

```
for d in distilled/clang/examples/*/; do lua5.4 "$d/program.lua" > "$d/expected.txt"; done
```

`scripts/check-expected.sh` re-runs the oracle for every entry and fails if a file differs.
