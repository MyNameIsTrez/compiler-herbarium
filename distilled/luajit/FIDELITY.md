# Fidelity: luajit

Real design being mimicked: LuaJIT 2.1, its trace compiler: trace recording, the trace IR and its snapshots, the loop optimization, and the assembler with its backwards register allocator.

Reference material used:

- Source: [LuaJIT/LuaJIT](https://github.com/LuaJIT/LuaJIT) at `c4b1e2f73a2e10fbcc637fcec474f639c38daafe` (branch `v2.1`, a shallow clone), `src/` only. Files read, in part: `lj_opt_loop.c` (the header comment, `loop_emit_phi`, `loop_subst_snap`, `loop_unroll`), `lj_ir.h` (the opcode list `IRDEF`, the reference layout around `REF_BIAS`), `lj_opt_fold.c` (`lj_opt_fold` entry, `lj_opt_cse`, the `SLOAD` rule `fwd_sload`), `lj_asm.c` (the register allocator from `ra_setup` to `ra_alloc1`, the snapshot allocation functions by name and `asm_snap_prep`, and `lj_asm_trace` in full), `lj_snap.c` (`snapshot_slots`, `snapshot_stack`), `lj_record.c` (`rec_for`, `rec_loop_interp`, `rec_loop_jit`), `lj_trace.c` (`lj_trace_hot`), `lj_dispatch.c` (`lj_dispatch_init_hotcount`) and `lj_jit.h` (the `SnapShot` struct and the `hotloop` parameter).
- Not read: `lj_asm_x86.h` (the instruction emitters, `asm_phi`, `asm_phi_shuffle`, `asm_loop`, `asm_head_root`'s callees), `lj_emit_x86.h`, `lj_snap.c` beyond the two functions above (in particular `lj_snap_restore`), `lj_record.c` beyond the loop functions (in particular `lj_record_ins`, where `needsnap` is consumed), the state machine in `lj_trace.c`, the other optimizations (`lj_opt_fold.c` rules, `lj_opt_narrow.c`, `lj_opt_mem.c`, `lj_opt_sink.c`, `lj_opt_dce.c`), `lj_bc.h`, the interpreter and the exit handler (`vm_x64.dasc`), and the machine code area (`lj_mcode.c`). No paper was read.
- The real tool was run, but not built from the commit above: the LuaJIT installed on the machine (`LuaJIT 2.1.1774896198`) was used for the comparison at the end of this file.

## Stage mapping

| Stage in this entry | Real stage name | Where it lives in the real source | Kept | Dropped or simplified |
|---------------------|-----------------|-----------------------------------|------|-----------------------|
| `stage_bytecode` | The bytecode that the Lua parser emits | Not read (`lj_bc.h`, `lj_parse.c`) | A register bytecode whose operands are slots of a frame | All of it. The bytecode is this entry's own small set, written by hand, not LuaJIT's |
| `stage_interpret` | The interpreter and its hot counters | `lj_dispatch_init_hotcount` in `lj_dispatch.c` and `lj_trace_hot` in `lj_trace.c` (the interpreter itself is `vm_x64.dasc`, not read) | A counter per loop that is decremented as the loop runs. When it reaches zero, recording starts at the loop and the interpreter keeps executing | The counter is `hotloop` (56 in the source) in LuaJIT and `HOTLOOP` (3) here, so the short example loop gets hot. LuaJIT keeps the counters in a small table indexed by a hash of the pc and counts in the loop instruction, this entry counts per jump back. No penalties after a failed trace and no blacklisting. The interpreter is a C `switch`, not assembler |
| `stage_record` | Trace recording | `rec_for`, `rec_loop_interp` in `lj_record.c`, `snapshot_slots` and `snapshot_stack` in `lj_snap.c`, the IR layout in `lj_ir.h` | Recording while the interpreter executes, with the concrete values deciding each branch. A slot is a ref, and the first read of a slot emits a type-guarded `SLOAD`. A comparison emits a guard after a snapshot whose pc is the other branch. Snapshots skip a slot that still holds its `SLOAD`. Recording stops when the next pc is the start of the trace, which is how `rec_loop_interp` closes a loop. Constants below `REF_BIAS` and instructions above it | The per-bytecode recorders of LuaJIT (not read) become four cases. Only integers (no numbers, tables, calls, upvalues, frames), no overflow-checked arithmetic, no narrowing. A snapshot has no frame links or pc encoding. Snapshots are not merged when no IR separates them. No constant sharing. A trace that leaves its loop while recording stops the program, where LuaJIT aborts the trace and goes on. Whether the next instruction after a guard starts a snapshot follows `J->needsnap` as set in `rec_for`; the code that consumes it, in `lj_record_ins`, was not read |
| `stage_loop` | The LOOP optimization | `loop_unroll`, `loop_subst_snap` and `loop_emit_phi` in `lj_opt_loop.c`, the `SLOAD` rule in `lj_opt_fold.c` | The recorded IR is the pre-roll, `LOOP` ends it, and the copy of it follows with every operand substituted. A copy that differs from the original it replaces gets a PHI. Snapshots are copied and substituted, with slots the snapshot does not mention filled in from the last snapshot. An `SLOAD` in the copy is replaced by what the slot holds at the end of the iteration, as `fwd_sload` does. A trailing snapshot with no guard after it is dropped | FOLD is that one rule, and there is no CSE, so nothing is hoisted out of the loop except a forwarded `SLOAD` (a re-emitted instruction that matches an earlier one would be, in the real code). `loop_emit_phi` passes 1, 2 and 4, which find redundant PHIs, are not there, and pass 3 (PHIs for variant slots without an `SLOAD`) is a check that stops the program instead. No type-instability fixes, no `CONV` or `ALEN` hints. |
| `stage_assemble` | `lj_asm_trace` | `lj_asm_trace` and the register allocator in `lj_asm.c` | The IR is walked from the last instruction to the first, and the code is written from the end of the buffer downwards. A value gets a register the first time the walk meets it (its last use) and gives it back at its definition. Hints steer a register choice. A guard allocates every register its snapshot needs. A PHI is met first, and the exit stubs and the jump back to the loop are emitted before the body, with the jump patched when the walk reaches `LOOP` | No spills, eviction or rematerialization (a trace that needs more than 8 registers stops the program). No dead-code skipping: `lj_asm_trace` skips an instruction with no register, this entry stops. No fusion of loads into operands, no commutation of operands, no copy of the left operand into the result register (the entry stops if the left operand is not already there). How the two sides of a PHI share one register and when that is legal is this entry's own reasoning, written from the allocator code and the `LOOP` comment, not from `asm_phi`, which was not read, and there is no shuffle. Instruction bytes are encoded by hand and checked by disassembling the output, not taken from `lj_emit_x86.h`. Register set, calling convention and stack layout are this entry's own |
| `stage_run` | Entering the trace and leaving it by an exit | `lj_snap_restore` and the exit handler (not read) | A failed guard jumps to a stub that names its snapshot and joins common code that saves the registers and calls a C function. That function walks the snapshot, stores the value of each slot (a register or a constant) into the frame, and returns the pc where the interpreter goes on | The stubs and the handler are this entry's own, from the general shape only. No frame restoration, no GC, no stack check, no trace linking, no side traces. code.bin has the address of the C function zeroed |

## Deliberate deviations

- Only a loop trace is made, and only the `loop` example gets one. The other examples have no loop that gets hot, so they run in the interpreter alone and have no `code.bin`. The Kind column of the README says Interpreter, because the real design is a VM and the JIT is what this entry is about.
- The hot threshold is 3 and not 56, so that a loop of ten iterations is traced. The interpreter runs the iterations before the threshold, one more under the recorder, and the trace runs the rest.
- The trace leaves through the snapshot of the loop's own condition. The interpreter resumes at the instruction after the loop, which is how a root trace of a loop ends in the real design too, but here there is no trace linking after that.
- Integer arithmetic wraps. LuaJIT's integer-valued arithmetic is overflow-checked or done on doubles.
- The bytecode, the values (16-byte tag and payload slots) and the call convention of the trace (frame base in `rbx`, the allocatable registers `rcx`, `rdx`, `rsi`, `rdi`, `r8` to `r11`, `rax` as a scratch for the exit) are this entry's own.

## Comparison with the real tool

The comparison used the LuaJIT that is installed on the machine, `LuaJIT 2.1.1774896198` from `/usr/local/bin`. It was not rebuilt from the pinned commit, so its output may differ a little from that commit's. The real tool was run on `examples/loop/program.lua` with the `jit.dump` module (`LUA_PATH="/usr/local/share/luajit-2.1/?.lua;;"`), and all five examples print exactly `expected.txt` under it.

- Command: `luajit -Ohotloop=3 -jdump=bitmsr examples/loop/program.lua`
- Matches: the trace is a pre-roll followed by a `LOOP` marker and a copy of the body, in which the invariant work stays above `LOOP`. The IR has the same operations and the same two `PHI`s at the end, one per loop-carried value. A trace has four snapshots, as here, and the exits of the loop carry the values of the loop variables. The loop body is `add`, `add`, a compare and a conditional jump back, with the values kept in registers across iterations.
- Differs: the real trace is recorded from the loop body (it starts at the `ADDVV`, with the compare after it), while this entry records from the compare, so the `LT` sits at a different place in the pre-roll. Real LuaJIT works on doubles (`num` `SLOAD`s and `addsd` in `xmm` registers, with constants inline) where this entry has integers in general registers. The real trace has a `RENAME` and a `movaps` before the `PHI`s are filled, which the entry has no equivalent of. The real code inverts the final compare so the loop jumps back directly with `ja`, where this entry ends the body with a compare, a jump out and an unconditional jump back. The real trace also begins with a few setup instructions that the entry has no equivalent of, and its exits go through exit stubs, where this entry has hand-written stubs. The code size, the addresses and the register names therefore differ.
