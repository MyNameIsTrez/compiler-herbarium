# Fidelity: luajit-interpreter

Real design being mimicked: the hand-written x86-64 assembler interpreter of LuaJIT 2.1 (`src/vm_x64.dasc`), its dispatch tables and hot counters (`lj_dispatch.c`), and the way it hands control to the trace compiler and takes it back through trace exits.

Reference material used:

- Source: [LuaJIT/LuaJIT](https://github.com/LuaJIT/LuaJIT) at `c4b1e2f73a2e10fbcc637fcec474f639c38daafe` (branch `v2.1`, a shallow clone). Files read, in part: `vm_x64.dasc` (the register defines, `ins_next`, `ins_callt` and `ins_call`, the tag macros, `branchPC`, the `hotloop` and `hotcall` macros, `vm_record`, `vm_hotloop`, `vm_hotcall`, `vm_exit_handler`, `vm_exit_interp`, and the bodies of ISLT, ISGE, the arithmetic macro `ins_arith` (integer path), KSHORT, MOV, CALL, CALLT, RET, RET0, RET1, FORL, LOOP, ILOOP, JLOOP, JMP, FUNCF and IFUNCF), `lj_dispatch.c` (`lj_dispatch_update`, `lj_dispatch_init_hotcount`, `lj_dispatch_call`), `lj_dispatch.h`, `lj_trace.c` (`lj_trace_hot`, `blacklist_pc`, `trace_stop`), `lj_bc.h` (the ordering asserts), `lj_jit.h` (the `hotloop` parameter), `lj_asm_x86.h` (`asm_exitstub_gen`) and `lj_parse.c` (`parse_while`, and the places that emit LOOP, RET0, RET1, CALL and FUNCF by name).
- Not read: `lj_trace_exit` and `lj_snap_restore`, `lj_dispatch_ins` and `lj_record_ins` (the recorder's entry), the vararg, table, upvalue, metamethod, float and string handlers of `vm_x64.dasc`, the GC and stack growth code, `vm_x86.dasc`, the ARM and PPC interpreters, and the `-DDUALNUM` build flags beyond what the integer paths show.
- The real tool was not run on the examples: the `luajit -bl` bytecode listing needs the `jit.*` Lua modules, and neither the installed LuaJIT nor a clone could run them here. The bytecode of the examples is written from `lj_parse.c`, not compared with a listing.

## Stage mapping

| Stage in this entry | Real stage name | Where it lives in the real source | Kept | Dropped or simplified |
|---------------------|-----------------|-----------------------------------|------|-----------------------|
| `stage_bytecode` | The bytecode that the Lua parser emits | `parse_while` and the emit sites in `lj_parse.c`, the word layout in `lj_bc.h` | The 32-bit instruction word, with the opcode in the low byte, A above it and D, or C and B, in the upper half. A `while` is its condition (comparison and a JMP out), then `LOOP`, the body, and a JMP back to the start of the condition. A conditional is the inverted comparison ISGE and a JMP. A function starts with FUNCF. A call has the function in slot A, a pc slot above it, then the arguments. The relative order of the opcodes, which the VM relies on (LOOP, ILOOP, JLOOP and FUNCF, IFUNCF are adjacent) | The bytecode is written by hand. Only integers, so no constant table of numbers beyond the one the examples use. KFUNC stands in for GGET, UGET and FNEW, which load a function. No vararg function (the main chunk uses FUNCF, where LuaJIT uses FUNCV), no CALLM or CALLT, no `nil` filling of missing parameters. No constant folding, so `arithmetic` keeps its unfolded operations, which is not what LuaJIT's parser would emit |
| `stage_assemble` | The interpreter, assembled by DynASM at build time | `vm_x64.dasc` | The pinned registers (BASE, PC, DISPATCH, KBASE, RA, RB/OP, RC/RD) with the names and, for the POSIX build, the same assignment. `ins_next` is the same six instructions and is copied into the end of every handler, so each has its own indirect jump. A call jumps through the first word of the callee, which is its function header. C functions are called through a FUNCC pseudo bytecode. Tagged values with the tag in the upper 17 bits, checked with a shift and a compare. Integer arithmetic with an overflow check. Frames of the shape `[BASE-16]` function, `[BASE-8]` return pc, with FRAME_C marking the bottom frame, and a return that restores BASE from the call instruction's A field | The assembler is a small C one run at startup, where DynASM runs at build time and its output is linked into `lj_vm`. Only the opcodes of the examples. No floats, no DUALNUM split, no tables, no metamethods (a type mismatch jumps to a `ud2`), no stack overflow check, no `nil` filling, no hooks, no `lj_vm_*` helper routines. The registers `r12` and `r13`, and the SSE state, are not touched. Absolute addresses are not in the code: everything is addressed from DISPATCH, so `code.bin` is the same on every run |
| `stage_dispatch` | The dispatch tables and the hot counters | `lj_dispatch_update` and `lj_dispatch_init_hotcount` in `lj_dispatch.c`, `lj_dispatch.h` | A dynamic dispatch table with an entry per opcode, and a static table (the length of the opcodes below FUNCF) that is never changed. While recording, the dynamic table sends every opcode below FUNCF to `vm_record`. The static table maps LOOP to the ILOOP handler, which does not count. A counter table of 64 16-bit counters, where a pc hashes to one. LOOP subtracts 2 and a call subtracts 1, and a counter that underflows leaves the interpreter. They start at `hotloop*2-1` | The threshold is 2 (56 in LuaJIT), so the example loop gets hot. Two dispatch modes (normal and recording) where `lj_dispatch_update` also has the instruction hook, call hook and profiler modes. No `GG_State` beyond the fields used. The static table holds JLOOP too, so a patched loop can run when recording stops |
| `stage_interpret` | Running the interpreter | `lj_vm_enter` and the bytecode handlers of `vm_x64.dasc` | Entering the VM with the bottom frame's function, leaving it when a return finds FRAME_C. A loop counter that underflows saves BASE and calls into C (`vm_hotloop`), which then redispatches the instruction through the static table. A function counter that underflows saves BASE and calls into C (`vm_hotcall`), after which `ins_next` continues. The 4-call threshold of FUNCF follows from the counter being decremented by 1 per call | No `lua_State`, no stack growth, no error unwinding. The call into C passes only the pc. In LuaJIT the hot call into `lj_trace_hot` can start recording from a function header too: here the function is blacklisted, which in LuaJIT's `blacklist_pc` patches FUNCF to IFUNCF as well, but LuaJIT only does this after repeated failed traces |
| `stage_record` | `vm_record` and the recorder | `vm_record` in `vm_x64.dasc`, `lj_trace_hot` and `lj_dispatch_ins` (not read) | While recording every instruction reaches the C hook first with the biased pc, and is then run by the interpreter through the static table. The start instruction itself runs through the static table too. Recording stops when the hook meets the start again. A comparison is recorded with its direction decided by the actual slot values | The hook records raw instructions and does not build IR. A loop that exits during recording stops the program, where LuaJIT aborts the trace. Instructions other than the loop's six stop the program |
| `stage_trace` | `trace_stop` and the assembler | `trace_stop` in `lj_trace.c`, `lj_asm_trace` (see distilled/luajit) | When recording ends the first LOOP is patched to JLOOP with the trace number in D, the dispatch table is restored, and the loop instruction is run again so it enters the trace. JLOOP loads the trace's machine code from a table indexed by D and jumps to it with BASE kept. A guard exit goes to a stub that pushes the exit number and jumps to the exit handler | The trace is made from a fixed template for each of the six instructions: no IR, no optimization, no registers except a scratch, no snapshots, no type guards and no overflow guard. The values stay in their stack slots. The code is assembled forwards, from the first instruction, and not backwards. Only one trace. See distilled/luajit for the trace compiler itself |
| `stage_exit` | `vm_exit_handler` and `vm_exit_interp` | `vm_exit_handler`, `vm_exit_interp` in `vm_x64.dasc` and `asm_exitstub_gen` in `lj_asm_x86.h` | The stub is `push` of the exit number then a jump to the handler. The handler pushes all the general registers so that the saved state is a struct, loads BASE from `jit_base` into the VM's saved base and clears `jit_base`, calls C with the saved state, and then restores the stack and resumes the interpreter with `ins_next` at the pc that C returned | Exit numbers are one byte pushed by one `push`, where LuaJIT reconstructs a larger number from two `push imm8`. The SSE registers are not saved. There is no snapshot restore: the one exit has only a resume pc, because the trace keeps its values in the slots. No trace exit counters, no side traces, no GC check, no `lj_trace_exit` |

## Deliberate deviations

- The interpreter is generated at startup, by an assembler written for this entry, from C calls that mimic the instructions of `vm_x64.dasc`. DynASM would produce the same bytes at build time. The point is that `code.bin` holds the interpreter itself, so the register assignment, `ins_next` and the dispatch jumps can be read as machine code.
- The code has no absolute addresses. LuaJIT's interpreter uses the `GG_State` addressed through DISPATCH for its tables too, but it calls C by `call extern` and the loader fixes that. Here every C function the VM calls is a pointer in the state block, so `code.bin` can be committed and compared.
- Hot threshold 2 and not 56, a counter table of 64 as in LuaJIT. The `_Alignas(256)` prototype array makes the counter slots (and so which instructions share one) the same on every build, and the dump prints them.
- The prototype keeps its constant pointer at a fixed distance before the first instruction, as `PC2PROTO(k)` does, but the layout is this entry's own.
- Function calls are never traced. The only counted call that gets hot, `fact`, is blacklisted, and the dump shows `vm_hotcall`.
- Only `loop` makes a trace. The other examples run in the interpreter alone and their `code.bin` has the interpreter only.
- The trace is machine code from templates, not from an IR. How a real trace is made is in distilled/luajit, which in turn has an interpreter in C. The two entries together cover both halves of LuaJIT.
- Ints wrap in the trace (no overflow guard). The interpreter handlers do check for overflow, and jump to the `ud2` that stands for the metamethod code.

## Comparison with the real tool

The real tool was not run on the examples, so no listing is compared. `luajit -bl` needs `src/jit/bc.lua` and `bcsave.lua`, which use Lua 5.3 operators and a conditional operator that the installed LuaJIT cannot parse, and running them from a clone was not allowed here. The constants to check against a real build are in the dump of `stage_dispatch`: the hot counter slots depend on the addresses of the bytecode in the real VM, and have nothing to compare with.

What can be checked against the source: the bytes of `ins_next` are the same as the ones that DynASM produces for `ins_next` (`mov eax, [rbx]`, `movzx ecx, ah`, `movzx ebp, al`, `add rbx, 4`, `shr eax, 16`, `jmp [r14+rbp*8]`), and `objdump -D -b binary -mi386:x86-64 -M intel code.bin` shows them at the end of every handler.
